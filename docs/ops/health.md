# Health check and monitoring (SCRUM-39)

Owner: Sonam Choki. Goal: see from one place which of the 20 services are up and which are down.

Every Jurwa service serves the standard gRPC health check (`grpc.health.v1.Health/Check`), which answers `SERVING` when the service is ready. Three things use it.

## 1. The script: `scripts/check-all-health.sh`

```bash
bash scripts/check-all-health.sh          # gRPC check on localhost:9001 ... 9020
HOST=10.0.0.5 bash scripts/check-all-health.sh
bash scripts/check-all-health.sh --k8s    # Kubernetes: ready pods against wanted pods
```

It prints one line per service, then a total, and exits with `0` when all are up and `1` when any is down (so CI or another script can use it). `2` means a usage error.

```
report-submission      9001   UP
...
feedback               9019   DOWN
analytics              9020   UP
19 up, 1 down
```

| Mode | What it checks | When to use it |
|---|---|---|
| default | `grpcurl` health check on `HOST:<port>`, 2 second timeout per service. The proto file `deploy/k3d/health.proto` is given, so a service without reflection works too | Services running with `make run`, or cluster ports forwarded with `kubectl -n jurwa port-forward svc/<name> <port>:<port>` |
| `--k8s` | `kubectl -n jurwa get deploy`: a service is UP when its ready pods reach the wanted number. A deployment scaled to 0, or missing, is DOWN | The cluster |

Needs `grpcurl` (default mode) or `kubectl` (`--k8s`). The script's own tests replace both with fakes, so they need nothing running:

```bash
bash scripts/tests/check-all-health_test.sh
```

## 2. Kubernetes probes (the monitor inside the cluster)

Every Deployment generated by `scripts/gen-k8s-manifests.sh` has two gRPC probes on the service port:

| Probe | Settings | What Kubernetes does when it fails |
|---|---|---|
| readiness | every 5 s, from 2 s after start | Takes the pod out of its Service, so no traffic reaches it. `kubectl get pods` shows `0/1` |
| liveness | every 10 s, from 10 s after start, 3 failures | Restarts the container. The `RESTARTS` column goes up |

So a service that stops answering is first hidden from traffic and then restarted, without anyone watching. The `--k8s` mode of the script reads the result of the readiness probe.

PostgreSQL, MongoDB and Redis have their own probes (`pg_isready`, a TCP check, `redis-cli ping`).

## 3. Grafana (Gayley, SCRUM-105)

`deploy/observability/` adds Prometheus and a Grafana dashboard "Jurwa services". Its **Pods up** panel shows `up{job="jurwa-pods"}`: 1 for each pod Prometheus can scrape, 0 when it cannot. The other panels show request rate, error rate and p95 duration per service. The script is the quick check from a terminal; Grafana shows the same over time.
